# Cradle 產品定位、軟體生命工程可行性與 Codex 整合分析

- 分析日期：2026-09-07
- 文件性質：產品策略分析與方向建議，不代表已核准的實作計畫。
- 分析依據：當時的專案文件、現行程式碼與 OpenAI 官方資料。
- 驗證範圍：未執行實際產品對照實驗；效益屬於判斷與待驗證假設。程式碼及外部產品能力可能隨後續版本改變。

## 核心判斷

**Cradle 的理想有可實現的核心，但產品重心需要更集中。Codex 越強，Cradle 越應該利用它的執行能力，把價值放在「軟體交付後，如何持續有證據地維護與改善」。**

如果 Cradle 的主要體驗仍是「輸入想法、呼叫模型、產生檔案、顯示成長」，它很容易被 Codex 取代。如果它能讓使用者少操心一批長期運作的軟體，又能清楚說明哪些可靠、哪些出問題、哪些需要人類決策，就有獨立價值。

## 一、Codex 帶來的定位問題

使用者現在從 Codex 得到的是一套完整的協作體驗：

- 可以逐步表達想法，不必一次寫完規格。
- AI 讀取實際工作環境，直接修改與執行。
- 遇到問題會調整做法，使用者可以途中補充方向。
- 使用者看到的是工作進展與成果。

這裡的價值不只來自模型，也來自上下文管理、工具、執行環境、互動方式與工作迴圈。

不能把競爭關係簡化成「Codex 做一次，Cradle 持續做」。Codex 已提供背景排程、自動化工作及多 Agent 工作管理；「持續執行」本身已經不足以構成差異。參考 [OpenAI Codex app 說明](https://openai.com/index/introducing-the-codex-app/)。

因此 Cradle 必須回答：

> 同樣使用 Codex，使用者為什麼還需要 Cradle？它具體替使用者省下哪一種責任與注意力？

## 二、目前產品定位與實作狀態

目前的 Cradle 可以描述為：

> 具有持久化軟體單位、產物管理與受控演化機制的工程平台原型，正在建立以證據判定品質的能力。

它已經超過單純的模型包裝，但還不能宣稱完成「不必例行人工校對」的目標。

| 面向 | 目前基礎與優點 | 缺口或限制 |
|---|---|---|
| Cell 身分與責任 | 有長期上下文、產物歸屬與責任邊界 | 還需要證明這些結構會降低實際維護成本 |
| Artifact 生產 | 已分離解析、正規化、驗證、修復與儲存 | 產物格式正確，不代表功能符合需求 |
| 品質判定 | 已有具版本的培養品質門檻與缺證據結果 | 培養流程的完整性，尚不等於產物的業務品質 |
| 演化 | 有生命週期政策、修復及結構操作基礎 | 不能由操作完成推導出架構真的變好 |
| 成熟度 | 有明確計算方式 | 指標仍需要與可靠性、維護成效建立實證關聯 |
| Provider 抽象 | 可替換推理來源 | 若只抽象成文字問答，會限制完整 coding agent 的能力 |

### 2.1 目前 Codex 接法尚未完整引入互動工作能力

[Codex adapter](../src/providers/codex-provider.js) 每次 `ask()` 都啟動獨立程序，使用：

```text
codex exec --json --ephemeral --sandbox read-only
```

執行目錄是隔離的暫存目錄，最後回傳回答文字。這適合受控推理與媒體分析，但目前這條接法沒有把 Codex 的持續對話、實際工作區修改與途中轉向能力完整帶進 Cradle。

### 2.2 培養品質與產物業務品質仍有差距

[培養品質政策](../src/situation/cultivation-quality-policy.js) 已有六個必要門檻：

- `source_integrity`
- `content_evidence`
- `cell_relevance`
- `memory_recorded`
- `artifact_integrity`
- `provenance_recorded`

這是實際進展，不能再說完全沒有 Quality Contract。

但這份判定回答的是「這次培養是否完成必要處理」。它沒有直接保證「使用者要求的功能已通過行為驗收」。

### 2.3 目標符合性檢查不等於行為正確性

[ArtifactValidator](../src/production/artifact-validator.js) 的目標符合性包含需求詞是否出現在檔案內容。這種檢查可攔截部分遺漏，卻不能證明行為正確。

例如，程式包含「權限」相關名稱，不代表未授權存取真的會被阻擋。

**目前最重要的落差，是「有處理與檢查」到「有足夠證據可以放心使用」之間的距離。**

## 三、軟體生命工程可以達成到哪裡

| 理想層次 | 可行性判斷 | 必要條件 |
|---|---|---|
| 軟體有長期身分、責任、歷史與可追蹤變更 | 高，已有工程基礎 | 持久化、版本、歸屬與狀態一致性 |
| 在明確範圍內，自動發現問題、修復、驗證與恢復運作 | 可行，適合作為近期核心 | 可執行驗收、隔離環境、修復預算、回復機制 |
| 任意軟體自行理解價值、形成架構、持續變好且幾乎不需人 | 目前無法合理承諾 | 尚缺通用的價值判準與可靠的演化驗證方法 |

最大的難題通常是：**系統如何知道自己真的變好了？**

例如「輸入 A 必須輸出 B」「舊版 API 必須相容」，相對容易建立機器可判定的條件。「這個介面更好用」「架構更合理」「報告更有洞察」，則需要更具體的使用情境與外部證據。

所以「人不用逐份校對」可以在特定範圍成立；「人不用定義什麼叫好」很難成立。

有限指標可以支持有範圍的品質承諾，但不能證明所有未觀察情境都正確。同一組測試重跑多次，可以增加對重現性的了解，不能補足缺失的需求覆蓋。

Cradle 的[品質模型文件](SOFTWARE_LIFE_QUALITY_MODEL.md)已經選對方向：缺少可觀測判準時，要回報 `insufficient_evidence`。

## 四、值得保留的優勢

### 4.1 長期責任可以脫離單次對話

一個服務的責任、相容性要求、事故紀錄與品質證據，不必依附某一段 Codex 對話。更換模型或開新工作階段後，仍能繼續維護同一個軟體單位。

[Artifact 歸屬政策](../src/production/artifact-ownership-policy.js)已提供部分基礎。

### 4.2 品質判斷可以成為可重現的系統結果

如果使用者能問「這個版本為什麼可以上線」，平台就能列出與版本綁定的驗收結果、環境與未解風險，價值會比一段「已完成」更持久。

### 4.3 人類注意力有機會集中到例外

對同時維護多個服務的人而言，重要的是知道哪一個需要介入，以及原因。這是 Cradle 可以爭取的產品價值，但仍需用實際工作證明。

## 五、缺點與風險

- **概念成本高。** 使用者可能只想維護一個服務，卻先要理解 Cell、DNA、Stimulus、成熟度與分裂融合。
- **過度編排可能降低效率。** 若小修改也需要多輪解讀、路由、反思與重生成，就可能比直接使用 Codex 更慢、更貴。
- **指標可能讓人過度放心。** 目前[成熟度計算](../src/dna/dna-maturity.js)結合 DNA 向量強度與歷史收斂程度；這有數學定義，但還不等同經驗證的軟體可靠性。
- **抽象可能限制底層工具。** 將完整 agent 壓成 `prompt → text`，會增加 Cradle 自己重建工作迴圈的負擔。
- **差異容易被追上。** 記憶、排程、多 Agent、修復等單項功能，都不能單獨視為長期優勢。
- **品質制度本身有成本。** 驗收規則、執行環境與觀測器也需要維護；省下的人工必須大於新增負擔。

## 六、結合 Codex 的建議方向

建議先讓 Codex 成為主要執行引擎，採取以下分工：

```text
使用者持續表達想法
          ↓
互動工作階段 ←→ Codex：理解、探索、修改、執行、修復
          ↓
Cradle：保留目標、責任邊界、版本與品質政策
          ↓
候選版本 → 驗收與證據 → 接受／修復／需要人決策
          ↓
持續觀察已接受版本
```

關鍵是讓 Codex 保留完成工作的自由度，同時讓 Cradle 管理哪些結果可以成為正式狀態。

官方 App Server 已提供持續對話、串流事件、核准互動，以及 `turn/steer` 途中補充指示和 `turn/interrupt` 中斷能力，適合嵌入自有產品。背景自動化則可考慮 Codex SDK。參考 [App Server 文件](https://developers.openai.com/codex/app-server)與 [SDK 文件](https://developers.openai.com/codex/sdk)。

「使用者邊輸入想法，AI 邊做事」有官方整合基礎；但接入介面並不自動保證與目前 Codex app 完全相同的體驗，仍需要處理工作階段、權限、重連與上下文。

### 整合原則

- Cell 可以跨越多個工作階段存在，不必與一條 Codex thread 永久一對一綁定。
- 使用者途中修改需求，Cradle 要保留目標版本，讓過期驗收證據失效。
- Codex 在隔離工作區修改候選版本，通過政策後才更新正式 Artifact。
- 執行者不能自行降低驗收門檻；新增測試可以協助，但不能任意改寫原本的驗收依據。
- Provider 中立應保留在領域層；不同執行工具可以宣告不同能力，不必全部退化成文字問答。

## 七、建議產品定位與第一個驗證

對外定位可以更具體：

> Cradle 讓你持續用自然語言改進軟體，並以可重現的驗收與觀測，管理它後續的品質和維護。

「Software Life Engineering」可以繼續作為設計理念。使用者首先應該看到：目標、正在做什麼、目前可用版本、驗收結果，以及需要決策的事情。

### 第一個驗證場景

**維護一個已有明確驗收案例的小型 API 服務，連續處理需求變更與故障修復。**

| 階段 | 要證明什麼 |
|---|---|
| 接入互動執行 | 在 Cradle 裡工作仍能持續補充需求、看到真實進展 |
| 完成品質閉環 | 能區分成功、功能失敗、缺少證據與驗證工具故障 |
| 驗證持續維護 | 隔天出現問題後，能保留脈絡、修復並重新取得有效證據 |
| 對照直接使用 Codex | Cradle 是否真的減少人工介入，且沒有提高錯誤接受率 |

### 對照方法

對照應使用同一模型版本、起始程式碼、任務與驗收條件，記錄：

- 人工介入時間。
- 端到端耗時。
- 執行成本。
- 錯誤接受率。
- 缺證據時是否正確升級處理。
- 建立和維護驗收制度的時間。

如果這個小場景不能比直接用 Codex 更省心，就應縮小 Cradle 為品質與維護工具；如果能做到，再擴大生命週期能力。分裂、融合、通用 DNA 演化可以暫時降低優先級。

## 結論

現在不需要放棄軟體生命工程。更值得調整的是實現順序：**先讓一個軟體單位能長期被可靠照顧，再證明更多生命隱喻帶來的價值。**

Codex 已經做得好的執行能力，正好可以降低這條路的成本。
